## Summary

GVE Level 3 Plugin and Action Contracts defines the application-independent contracts and registry rules through which the core resolves plugins, selected plugins resolve their own actions, actions declare and interpret their inputs, and exactly one fresh uniquely attributable validated operation contract is produced for each accepted operation. It assigns plugin registration to the core-owned plugin registry, action registration to plugin-owned action registries, requires deterministic validated and sealed registry snapshots, and preserves plugin and action ownership of application-specific meaning.

## Definitions

### Common plugin contract (`L3-PAC-COMMON-PLUGIN-CONTRACT`)

The application-independent contract enforced by the core for one plugin, including stable plugin identity, compatible plugin-interface version, one plugin-owned action registry, and the common facts needed for deterministic registration and resolution without exposing action-specific meaning.

### Common action contract (`L3-PAC-COMMON-ACTION-CONTRACT`)

The application-independent contract enforced by an owning plugin for one action, including stable action identity, compatible action-interface version, one declared input contract, and the common capabilities required to interpret and contract one governed operation.

### Plugin registration (`L3-PAC-PLUGIN-REGISTRATION`)

The explicit association of one plugin identity and common plugin contract with the core-owned plugin registry before that registry is validated and sealed.

### Action registration (`L3-PAC-ACTION-REGISTRATION`)

The explicit association of one action identity and common action contract with exactly one owning plugin's action registry before that registry is validated and sealed.

### Plugin resolution (`L3-PAC-PLUGIN-RESOLUTION`)

The core-owned deterministic resolution of one requested plugin identity to exactly one compatible registered plugin using only application-independent plugin-registry facts.

### Action resolution (`L3-PAC-ACTION-RESOLUTION`)

The selected-plugin-owned deterministic resolution of one requested action identity to exactly one compatible registered action in that plugin's sealed action registry.

### Declared action input contract (`L3-PAC-DECLARED-INPUT-CONTRACT`)

The complete action-owned declaration of required, optional, forbidden, and structurally constrained inputs for that action, together with the action-owned rules needed to interpret their application-specific meaning.

### Structural input conformance (`L3-PAC-STRUCTURAL-INPUT-CONFORMANCE`)

The application-independent determination that supplied input has the declared shape, presence, identity, and representation required by an action contract, without interpreting the application's semantic meaning.

### Action-owned interpretation (`L3-PAC-ACTION-INTERPRETATION`)

The selected action's authoritative interpretation of its supplied inputs, governing authority, and requested operation meaning after structural conformance has been established.

### Validated operation contract (`L3-PAC-VALIDATED-OPERATION-CONTRACT`)

The single fresh immutable contract produced for one successfully interpreted operation and uniquely attributable to the workflow, operation, selected plugin, selected action, interface versions, registry snapshots, governing authority, and complete interpreted inputs that produced it.

### Validated-contract freshness (`L3-PAC-CONTRACT-FRESHNESS`)

The property that a validated operation contract was produced from the current operation content, complete interpreted inputs, selected plugin and action, compatible interface versions, sealed registry snapshots, and governing authority and has not been invalidated or superseded.

### Registry validation (`L3-PAC-REGISTRY-VALIDATION`)

The fail-closed determination that a plugin or action registry is complete, deterministic, internally compatible, free of duplicate or conflicting identities, and suitable to become immutable for one planning and execution attempt.

### Sealed registry snapshot (`L3-PAC-SEALED-REGISTRY-SNAPSHOT`)

A uniquely identifiable immutable snapshot of a validated plugin registry or action registry after which registration, replacement, identity mutation, and interface-version mutation are forbidden for the governed attempt.

### Validated-contract attribution (`L3-PAC-CONTRACT-ATTRIBUTION`)

The deterministic binding of exactly one validated operation contract to all identities, versions, snapshots, authority, and interpreted inputs that govern one operation.

## Normative requirements

### L3-PAC-REQ-001

Each governed operation must request exactly one nonempty plugin identity and exactly one nonempty action identity owned by that plugin; missing, multiple, conflicting, or ambiguous requested identities must fail closed.

References: `L3-PAC-PLUGIN-RESOLUTION`, `L3-PAC-ACTION-RESOLUTION`, `L3-RO-OPERATION-REPRESENTATION`

### L3-PAC-REQ-002

Plugins must register only with the core-owned plugin registry through the common plugin contract, and each plugin identity must resolve to at most one compatible registered plugin.

References: `L3-PAC-COMMON-PLUGIN-CONTRACT`, `L3-PAC-PLUGIN-REGISTRATION`, `L3-RO-PLUGIN-REGISTRY-OWNER`

### L3-PAC-REQ-003

Actions must register only with exactly one owning plugin's action registry through the common action contract and must not register directly with the core.

References: `L3-PAC-COMMON-ACTION-CONTRACT`, `L3-PAC-ACTION-REGISTRATION`, `L3-RO-ACTION-REGISTRY-OWNER`

### L3-PAC-REQ-004

The core must complete deterministic plugin resolution before action resolution, and only the selected plugin may resolve the requested action from its own validated sealed action-registry snapshot.

References: `L3-PAC-PLUGIN-RESOLUTION`, `L3-PAC-ACTION-RESOLUTION`, `L3-PAC-SEALED-REGISTRY-SNAPSHOT`, `L3-RO-PLUGIN-INTERFACE-BOUNDARY`

### L3-PAC-REQ-005

The core may validate common plugin-contract identity, interface-version compatibility, registry attribution, and structural conformance, but must not interpret, derive, normalize, override, compare, or validate plugin-owned action or input meaning.

References: `L3-PAC-COMMON-PLUGIN-CONTRACT`, `L3-PAC-STRUCTURAL-INPUT-CONFORMANCE`, `L3-RO-CORE-ORCHESTRATOR`, `L3-RO-PLUGIN-INTERFACE-BOUNDARY`

### L3-PAC-REQ-006

Each action must own one complete declared input contract and must retain authoritative application-specific interpretation of every supplied input and the requested operation meaning.

References: `L3-PAC-DECLARED-INPUT-CONTRACT`, `L3-PAC-ACTION-INTERPRETATION`, `L3-RO-ACTION-INTERFACE-BOUNDARY`

### L3-PAC-REQ-007

Structural input conformance must be evaluated before action interpretation; missing required input, forbidden input, duplicate input identity, malformed representation, or structural mismatch must fail closed without inventing action-specific meaning.

References: `L3-PAC-DECLARED-INPUT-CONTRACT`, `L3-PAC-STRUCTURAL-INPUT-CONFORMANCE`, `L3-PAC-ACTION-INTERPRETATION`

### L3-PAC-REQ-008

One successfully resolved and interpreted operation must produce exactly one fresh, valid, immutable, and uniquely attributable validated operation contract; zero contracts, multiple contracts, reused contracts, or non-unique attribution must fail closed.

References: `L3-PAC-VALIDATED-OPERATION-CONTRACT`, `L3-PAC-CONTRACT-FRESHNESS`, `L3-PAC-CONTRACT-ATTRIBUTION`

### L3-PAC-REQ-009

Every validated operation contract must bind the current workflow identity, operation identity, plugin identity, action identity, plugin-interface version, action-interface version, plugin-registry snapshot identity, action-registry snapshot identity, governing authority, and complete interpreted inputs.

References: `L3-PAC-VALIDATED-OPERATION-CONTRACT`, `L3-PAC-CONTRACT-ATTRIBUTION`, `L3-PAC-SEALED-REGISTRY-SNAPSHOT`, `L3-RO-WORKFLOW-REPRESENTATION`, `L3-RO-OPERATION-REPRESENTATION`

### L3-PAC-REQ-010

A validated operation contract must be fresh for every fact to which it is bound; any change to operation content, interpreted inputs, selected plugin or action, interface version, registry snapshot, or governing authority must invalidate the prior contract and require fresh production.

References: `L3-PAC-CONTRACT-FRESHNESS`, `L3-PAC-CONTRACT-ATTRIBUTION`

### L3-PAC-REQ-011

Before a planning or execution attempt, the core-owned plugin registry and every participating plugin-owned action registry must be complete, validated, deterministic, sealed, uniquely identified, and immutable for that attempt.

References: `L3-PAC-REGISTRY-VALIDATION`, `L3-PAC-SEALED-REGISTRY-SNAPSHOT`, `L3-RO-IMMUTABLE-RUNTIME-SNAPSHOT`

### L3-PAC-REQ-012

Duplicate registration, late registration, unavailable identity, unauthorized registration, conflicting ownership, ambiguous resolution, identity mutation, incompatible interface version, incomplete registry validation, or registry snapshot drift must fail closed.

References: `L3-PAC-PLUGIN-REGISTRATION`, `L3-PAC-ACTION-REGISTRATION`, `L3-PAC-REGISTRY-VALIDATION`, `L3-PAC-SEALED-REGISTRY-SNAPSHOT`

### L3-PAC-REQ-013

A missing, malformed, unauthorized, stale, incompatible, conflicting, duplicate, incomplete, or non-uniquely attributable validated operation contract must fail closed and must not be repaired by inference, fallback selection, or reuse.

References: `L3-PAC-VALIDATED-OPERATION-CONTRACT`, `L3-PAC-CONTRACT-FRESHNESS`, `L3-PAC-CONTRACT-ATTRIBUTION`

### L3-PAC-REQ-014

Each action must have an independently identifiable source module and one explicit registration entry in its owning plugin; adding an action must not require core modification or modification to unrelated action implementations.

References: `L3-PAC-ACTION-REGISTRATION`, `L3-RO-ACTION-MODULE-BOUNDARY`, `L3-RO-ACTION-REGISTRY-OWNER`

Registry validity, successful resolution, structural conformance, action interpretation, and validated-contract production establish no workflow-plan acceptance, operation eligibility, attempt, completion, observation, verification, effect, evidence sufficiency, or authoritative result claim.

Contract and evidence freshness must bind to stable governed identities sufficient to detect relevant change, including operation content, selected plugin identity, governed instruction set revision, governing authority context, workflow-plan attempt, result-realization attempt, observation context, and freshness boundary. Freshness must not be established by an unbound Boolean assertion, and this requirement does not prescribe a specific digest, cryptographic algorithm, storage mechanism, or transport.
